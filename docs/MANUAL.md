# trade システム取扱説明書（M1〜M6）

このドキュメントは、現在のシステム（M1〜M6）を**専門知識がなくても評価・制御できる**ように、
平易な日本語で書いた取扱説明書です。専門用語は使うたびにその場で説明します。

---

## 0. これは何か（1分で）

- **「固定したルールで賭けるbot」ではありません。** 「売買ルールを探し続け、厳しく検査し、
  合格したものだけを少しずつ採用し、ダメになったら捨てる工場」です。
- 計算はすべて **GitHub Actions（無料枠）** で動き、インフラ費用ゼロ。
- **git（バージョン管理）が“記憶”** です。データ取得・発見した戦略・売買・損益のすべてが
  コミット（変更履歴）として残り、後から差分で追えます。
- **いまは「ペーパー（仮想資金）」のみ**で動きます。**実弾（本物のお金）は既定でOFF**です。

## 1. システム全体のデータの流れ

```
 ①取得 → ②保存 → ③探索/発明 → ④検査 → ⑤養生 → ⑥採用 → ⑦執行 → ⑧記録
                                   ↑                                  │
                                   └────────── ⑨監視（劣化したら退役）←┘
```

| 段階 | 担当（コマンド/ジョブ） | 何をするか | 出力の保存先 |
|---|---|---|---|
| ①取得 | `sync-data`（data-sync） | bitbankの価格を取得（1時間足）。4時間足・日足は1時間足から合成。Binanceは研究用の長期履歴、Alpacaは米株（キー設定後） | `data/ohlcv/...parquet` |
| ②保存 | 同上 | 価格表（ローソク足）を追記保存。重複・遅延に強い（何度流しても壊れない） | `data/ohlcv/` |
| ③探索/発明 | `research`（research-nightly） | **optuna**が既存戦略の良いパラメータを探し、**GP**が新しい数式を発明する | （④へ） |
| ④検査 | 同上（検査ゲート） | 各候補を後述の厳しい検査にかける。合格＝「養生中」、不合格＝「候補止まり」として台帳に記録 | `state/population.db`、`state/trial_ledger.json` |
| ⑤養生 | `promote`（executor-paper / research-nightly） | 発見後に**新しく届いたデータ**だけで再評価（後述） | `state/population.db` |
| ⑥採用 | 同上 | 養生に合格したものだけ「採用」。実際に動かす配分を書き出す | `state/champions.json` |
| ⑦執行 | `paper-step`（executor-paper） | 採用戦略を読み、確定した足で目標ポジションを計算→**現在との差分だけ**仮想売買 | `state/paper/account.json`,`fills.parquet`,`equity.parquet` |
| ⑧記録 | `report` | 人間が読むレポート（採用戦略・建玉・損益・約定）を生成 | `state/reports/latest.md` |
| ⑨監視 | `promote` | 採用中の戦略を毎回点検し、劣化（減衰）したら退役・現金化 | `state/population.db`,`state/champions.json` |

**重要な性質**
- **先読み禁止**: 戦略は「確定した足（締まったローソク）」だけで判断します。未来の値は一切使いません。
- **冪等（べきとう）**: 同じ場面で2回動いても二重に売買しません（目標と現在の差分だけ売買するため）。
- **すべて記録**: どの戦略をいつ採用/退役したかも含め、全部gitの履歴に残ります。

## 2. 「ルールの合否判定基準」の具体的な仕組み

候補は何千個も試すので、「一番成績の良かったバックテストを選ぶ」だけでは**必ず“まぐれ当たり”を掴みます**。
それを防ぐのが、以下の三段構えの関門です。

### 2-1. 検査ゲート（M2）— 最初の関門（全候補が通る）

5つの基準を**すべて**満たして初めて次へ進めます（既定値）。

| 基準 | 平易な意味 | 合格ライン |
|---|---|---|
| DSR（割引シャープ） | 「何千個も試した中のまぐれ」を差し引いても本物の実力か。**試した数が多いほど厳しくなる** | ≥ 0.95 |
| PBO（過剰適合確率） | 期間を入れ替えると勝ち戦略が入れ替わってしまう＝まぐれ、の度合い | ≤ 0.20 |
| SPA（優位性検定のp値） | 「何もしない」に対して**本当に**勝っているか（多数比較の下駄を補正） | ≤ 0.05 |
| CPCV OOS中央値 | 期間を組み替えた多数の“本番想定”成績の真ん中がプラスか | ≥ 0 |
| CPCV プラス率 | それら本番想定の半分超でプラスか | ≥ 0.5 |

- **DSRがこの仕組みの肝**です。GPやoptunaが試した回数を `trial_ledger.json` に累積し、
  「これまで合計◯万個試した中の最良」として正しく割り引きます。試行が増えるほど基準が自動的に上がります。
- **自己テスト**: 純粋な乱数（中身のないノイズ）を入れると、このゲートが必ず「不合格」になることを
  自動テストで保証しています＝検査が機能している証明です。

### 2-2. 養生（ようじょう）ゲート（M5）— 実弾の手前の砦

検査ゲートに通っても、まだ**採用しません**。「養生中」として、本物かどうかを前方データで確かめます。

- 発見した瞬間の「最後の足の時刻」を記録します。
- 以後、**その時刻より後に届いた新しいデータ**（探索が一度も見ていない、本当の意味での“ぶっつけ本番”）
  だけで戦略を計算し直します。
- **採用条件（すべて満たす）**:
  1. 新データが最低 **60本** たまっていること
  2. その前方成績（シャープ）が**プラス**であること
  3. 前方シャープが「バックテストのシャープの信頼下限（おおよそ95%）」を**下回らない**こと
- 満たして初めて「採用（champion）」に昇格し、配分が付いてペーパーで実際に動きます。

### 2-3. 減衰退役（M5）— 採用後の見張り

採用後も毎回、新データで点検します。次の**どれか一つでも**該当したら、退役（現金化）します。

- 前方シャープが上記の信頼下限を割った
- 「下方シフト検知」（途中から明らかに成績が落ちた、を統計的に検知）
- 前方の最大損失（ドローダウン）がバックテストの **1.5倍** を超えた

### 2-4. GP（M6）も**まったく同じ関門**を通る

GP（新しい数式の発明）は「候補を作る」だけです。作った式は 2-1 → 2-2 → 2-3 と、
他の戦略と**完全に同じ**関門を通ります。しかもGPは試行回数が桁違いに多いため、
DSRの割引が特に強くかかり、**採用されにくく**なっています（これは意図的な設計です）。

## 3. 緊急停止（キルスイッチ）手順

### 仕組み
`state/KILL_SWITCH` という名前のファイルが**存在するだけ**で、執行は発注の前に
**全ポジションをフラット化（手仕舞い）して停止**します。サーバーやGUIは不要です。

### 発動手順（どの端末からでも、GitHub上だけで完結）
1. リポジトリに `state/KILL_SWITCH` というファイルを作る（中身は空でも可）。
   - PCのgit: `touch state/KILL_SWITCH`
   - スマホ/ブラウザ: GitHubの「Add file」→ファイル名を `state/KILL_SWITCH` にして作成
2. **commit して push**（GitHub上なら「Commit changes」を押すだけ）。
3. 次の執行サイクル（最大1時間以内）で、自動的に全建玉を解消して停止します（ペーパー・実弾とも）。

### 解除手順
`state/KILL_SWITCH` を**削除して commit & push**すれば再開します。

### 実弾の二重ロック（さらに安全）
- 実弾は**そもそも既定でOFF**です。動くのは「リポジトリ変数 `LIVE_ENABLED=true`」かつ
  「取引専用APIキー（出金不可）を設定」した場合**だけ**。
- 一時的に止めたいだけ → **キルスイッチ**で十分。
- 実弾を完全に断ちたい → リポジトリ変数 `LIVE_ENABLED` を消す（または `false` に）。

## 4. あなたがシステムを評価・制御するための早見表

**何を見ればよいか**
- `state/reports/latest.md` … いま採用中の戦略・建玉・損益・最近の約定（人間用サマリ）
- `state/champions.json` … いま実際に動いている戦略と配分
- `state/population.db` … すべての候補の状態（候補/養生中/採用/退役）と指標（SQLite）
- `state/trial_ledger.json` … これまでの累積試行回数（DSRの厳しさの源）

**どこを変えると挙動が変わるか（M7以降で調整する主なつまみ）**
- 検査の厳しさ … `GateThresholds`（DSR下限0.95、PBO上限0.2、SPA上限0.05 など）
- 養生・退役の厳しさ … `PromotionConfig`（養生に必要な本数60、信頼区間の幅、DD倍率1.5 など）
- リスク上限・配分 … `RiskLimits`（1銘柄あたり上限、総建玉上限）
- 対象銘柄 … `strategies_config/universe.yaml`

**既定で効いている安全装置**
実弾OFF／現物は空売り禁止／レバレッジなし／無取引バンド（過剰売買防止）／日次・最大DD監視／キルスイッチ。

## 5. GP（数式の自動発明）についての正直な見解

> 「価格データだけを入力に、GPで数式をランダム進化させて持続的な優位性（アルファ）を見つけるのは、
> 極度の過剰適合を生むだけで、ほぼ不可能」——この見方は**おおむね正しい**です。

詳しくは本文（チャット）の回答を参照。要点だけ:

- **強い主張（価格だけのGPで“魔法の数式”が見つかる）には、私も懐疑的です。** 試行が膨大→まぐれが必ず混じる、
  価格情報は薄く効率的、見つけても混雑で消える——という批判は妥当です。
- だからこそ本システムは **「GPは提案するだけ／採否は厳格なゲートが決める」** 設計です。
  今回テストでGPの生成物が**全却下（採用ゼロ）**だったのは、**失敗ではなく設計通りの正常動作**です
  （DSR・PBOが、見栄えする式を“まぐれ”として正しく弾いた）。
- **現実的な期待値**: GPは生成物の**大半（おそらく99%超）を却下**し、長期間ゼロ採用も普通。たまに弱い分散源が
  生き残れば儲けもの、という位置づけ。**主力ではなく、厳重に管理された実験**として扱うのが妥当です。
- **推奨**: ①GP由来はゲートをさらに厳しく＆養生を長く、②GPの配分上限を低く、③将来は価格以外の入力
  （横断・ファンディング・レジーム特徴量）を足す。価格のみ・単一銘柄のGPは、批判が最も当てはまる弱い設定なので。
