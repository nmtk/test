# 運用戦略 — なぜ通らなかったか、何を変えたか、これからどう回すか

このドキュメントは 3 つの問いに答える。

1. **診断** — なぜ 75,000 回以上の試行がすべて検証ゲートで落ちたのか
2. **打ち手** — 何を実装したか（資金フロー・コンテキストレイヤー）
3. **運用** — 人間（あるいは Claude）が毎回考えなくても、エンジンが有効な戦略を

## 1. 診断: ゲートは壊れていない。仮説空間が狭すぎた

`state/reports/latest.md` の全 45 ファミリーの敗因を分解すると:

| ファミリー | 典型的な落ち方 | 意味 |
|---|---|---|
| tsmom / ma_cross / donchian | DSR 0.0〜0.8（基準 0.95）、PBO 0.3〜0.9 | エッジ自体が弱い。7.5 万回の試行で正直にデフレートすると偶然と区別できない |
| zscore_reversion | ほぼ全部 Sharpe 0.00 | 手数料 15bps を払うと取引が発生しないか損失 |
| gp | **DSR 1.000 / SPA p 0.002 でも PBO 0.1〜0.7 で落ちる** | イン・サンプルの当たりは強いが「その選択自体」が過学習 |

重要なのは、これは**システムの失敗ではなく、正しい動作**だということ。
単一銘柄の価格チャートだけから作れるシグナル（トレンド・ブレイクアウト・平均回帰）は
世界で最も混雑した仮説空間であり、正直な多重検定補正を掛ければ落ちるのが自然。
ゲートを緩めれば「チャンピオン」は出るが、それは実弾で溶けるチャンピオンになる。

**結論: ゲートではなく、探索する情報の次元を変える。**

## 2. 打ち手: 資金フロー・コンテキストレイヤー

ユーザー仮説 —「運用商品のチャートだけでなく、金利・株式・金・ドルを見て、
資金がいつ流入し、いつ他の資産へ逃げるかを条件にすべき」— をエンジンの
第一級の探索次元にした。

### データ (Job A が毎回同期)

`strategies_config/context.yaml` に定義。全て**鍵不要の無料ソース**:

| key | 何を測るか | ソース |
|---|---|---|
| `spx` | 株式のリスク選好（リスクオン/オフ） | FRED `SP500` |
| `gold` | 質への逃避の受け皿 | stooq `xauusd`（ベストエフォート） |
| `us10y` | 資金の値段（緩和/引き締め） | FRED `DGS10` |
| `usdjpy` | 建玉通貨 JPY 自体の動き | FRED `DEXJPUS` |
| `eurusd` | ドル指数プロキシの材料 | FRED `DEXUSEU` |

> **2026-07-12 修理**: 当初は全系列 stooq だったが、GitHub Actions ランナーからの
> リクエストに stooq が全て 404 を返し続けたため（6 日間フロー特徴量が中立 0.0 の
> まま動いていた）、FRED（米政府ホスト・データセンター IP を遮断しない）を主ソース
> に切替。FRED に日次系列がない gold のみ stooq に残し、ブラウザ User-Agent を付与。
> gold が取れない間は設計どおり中立 0.0 に退化する。

さらに外部データなしで作れる**クリプト内フロー**: BTC 市場全体のモメンタム
（`ctx_btc_mom`）、対 BTC 相対力 = アルトへのローテーション（`ctx_rel_btc_mom`）、
対 BTC 連動度（`ctx_btc_corr`）。

### 特徴量 (`engine/features/context.py`)

全て [-1, 1] に有界・因果的（**前日以前の確定値のみ**。日次バーはクローズ時刻
ベースの as-of 結合で、当日の値は翌 UTC 日まで見えない。さらにバックテスターが
ウェイトを 1 バーずらすので二重に安全）。データ欠損時は中立 0.0 に退化し、
実行は止まらない。

### 探索への注入は 2 経路

1. **人間設計の仮説: `macro_flow` アーキタイプ** — 「ゲート条件を満たす地合いの
   ときだけトレンドに乗る」。ゲートは `risk_on` / `dollar` / `spx` / `us10y` /
   `usdjpy` / `gold` / `btc` / `rel_btc` から optuna が選ぶ。`direction` パラメータが
   順仮説（流入時に参加）と逆仮説（流出時に参加）の両方を試す。
2. **自動発見: GP 端子の拡張** — GP の特徴量端子が 5 個 → 20 個になり、夜間の
   進化が「ドル安のときだけ効くトレンド」のようなフロー条件付きアルファを
   **人間の介在なしに**合成・淘汰する。これが「Claude の頭脳なしでも戦略を
   立て続ける」の実体。

検証ゲートは**一切緩めていない**。同じ CPCV → PBO → DSR → SPA を、より情報量の
多い仮説空間に適用する。

## 3. 運用: 工場の回し方

### 何もしなくても回るもの

- Job A（30 分毎）: 銘柄 OHLCV + コンテキスト系列の同期
- Job D（毎晩）: `macro_flow` を含む全アーキタイプの探索 + フロー端子付き GP 進化
  → ゲート → 合格者は incubating へ
- 昇格 FSM: シャドー養生 → カナリア → チャンピオン。実弾はカナリア上限まで

### 週次で見るもの（5 分）

1. `state/reports/latest.md` の **Pipeline 行** — `incubating` が 0 より大きく
   なった週が最初のマイルストーン
2. macro_flow / gp テーブルの **pbo と dsr の推移** — dsr が高く pbo だけで落ちる
   候補が増えてきたら、仮説空間が「当たりに近い」シグナル
3. data freshness（`uv run trade status`）— コンテキスト系列（fred / stooq）が
   止まっていないか（`data/ohlcv/fred/` に前週より新しい行があるか）

### 新しいフロー仮説の足し方（コード 1 行 + YAML 1 行）

1. `strategies_config/context.yaml` に系列を追加（例: FRED の `DGS2`、stooq の
   `^ndq`）
2. `engine/features/context.py` の `CONTEXT_KEYS` に key を追加
3. 何もしなくても: Job A が同期 → `ctx_{key}_mom` / `ctx_{key}_trend` が生成 →
   GP が翌晩から端子として使い、ゲートが検証する

### 仮説バックログ（優先順）

| 仮説 | 必要データ | メモ |
|---|---|---|
| 資金調達率（perp funding）— 過熱の逆張り | Binance fapi（鍵不要） | クリプト固有で混雑が比較的少ない |
| ステーブルコイン時価総額の増減 = クリプトへの待機資金 | 要ソース調査 | 「資金流入」の最も直接的な計測 |
| 曜日・時間帯効果 × フローゲート | 既存データのみ | 特徴量追加だけで試せる |
| 2s10s イールドカーブ（景気後退シグナル） | FRED `T10Y2Y` | context.yaml + CONTEXT_KEYS で 1 行 |
| BTC 半減期サイクル位相 | 既存データのみ | 長期レジームの事前分布として |

### やってはいけないこと

- **ゲートの閾値を下げる** — 75,722 回の試行台帳が既に DSR を厳しくデフレート
  している。閾値を下げても「本物のエッジ」は増えない
- 同じ仮説空間で trials だけ増やす — 台帳が膨らみ、将来の本物の候補まで
  デフレートで殺す。**試行は「新しい情報次元」に使う**
- 落ちた候補のパラメータを手で微調整して再投入する — それは PBO が測っている
  「選択の過学習」そのもの

## 4. 期待値の管理

このシステムの成功条件は「毎週チャンピオンが出る」ことではない。
**「出たチャンピオンが、実弾で背負える程度に本物である確率が高い」**こと。
フローレイヤーは合格確率を上げる最も筋の良い一手だが、それでも大半の夜は
全滅が正常である。焦って緩めた瞬間に、このシステムは「よくある過学習ボット」に
退化する。番人はコードが務める。人間は仮説の供給と、上の表の週次 5 分だけでいい。

## 5. アルファプール — PBO ボトルネックの構造的解消（2026-07-12）

### 診断の更新: ボトルネックは DSR から PBO に移った

フローレイヤー導入後 6 晩（累積 約 126,000 試行）の本番結果:

- GP ファミリーは 9 件中 8 件が **DSR ≥ 0.99・SPA p ≈ 0・CPCV 中央値 +1.4〜+3.1**
  を達成。つまり「偶然では説明できない、アウトオブサンプルでも効く」水準に到達
- しかし **9 件全てが PBO だけで落ちた**（基準 ≤ 0.10 に対し 0.24〜0.73）

PBO（CSCV）が測るのは「イン・サンプル最良の 1 本を argmax で選んだとき、その 1 本が
アウトオブサンプルでも上位に残るか」。殿堂入り 12 本がどれも同水準に優秀なら、
その中の 1 位選びはコイン投げに近く、**メンバー全員が本物でも PBO は 0.5 付近に張り付く**。
つまり落ちていたのは戦略ではなく「兄弟の中から 1 本だけ選ぶ」という運用方式そのもの。

### 打ち手: argmax をやめ、プールを運用単位にする

`ensemble` アーキタイプ（`engine/strategies/ensemble.py` + `engine/search/ensemble.py`）:

1. 毎晩の探索後、その (銘柄, 足) の**各アーキタイプのベスト設定 + GP 殿堂入り**を
   候補メンバーとして集める（retired は除外）
2. 各メンバーのネットリターンで頑健スコア（CPCV 中央値）を取り、**負けているものは捨てる**
3. リターン相関 > 0.9 のメンバーは同一ベットとみなし、高スコア側だけ残す（貪欲除去）
4. 残った上位 K 本（K ∈ {2,3,5,8}）× 重み付け（等ウェイト / 逆ボラ）で
   **固定ウェイトのプール変種**を作り、その変種ファミリーを**そのままのゲート**に掛ける
5. 合格すれば通常どおり incubating → 昇格 FSM → 紙運用。チャンピオンの params には
   メンバーと凍結ウェイトが全部入っており、実行側は他の戦略と同じに再構築するだけ

なぜこれで通るのか（ゲートを緩めずに）:

- **PBO**: プール変種同士は「広さ」「重み付け」という構造的な違いなので、イン・
  サンプル 1 位がアウトオブサンプルで崩れる理由がノイズ適合ではなくなる。argmax の
  不安定性という PBO が正しく罰していた欠陥を、運用方式の側から取り除く
- **DSR**: 相関の低いメンバーの合成はシャープを実力で引き上げる（分散低減）。しかも
  プールの DSR は自分の試行数に加えて**メンバー系列の累積試行数（最大値）を継承して**
  デフレートする — どのファミリーよりも厳しい会計
- これは実務のマルチアルファ運用（シグナルブレンディング）の標準形であり、
  指標ハックではない

補助として GP の殿堂入り自体にも**相関キャップ（0.95）**を入れた
（`GPConfig.hof_corr_cap`）。殿堂がチャンピオンのクローン 12 本で埋まらず、
プールの材料が本当に分散した賭けになる。

## 新アーキタイプ 2 本: `wemof` と `trade_balance`

USD/JPY を狙った 2 つの仮説を追加した。どちらも**検証ゲートは未通過**で、
チャンピオンには入れていない。以下はその設計と、**なぜ落ちたか**の記録。

### 1. `wemof` — 「説明のつかない値動きだけ獲る」逆張り

わっきゃい氏が公開している WEMOF（Wakkyai's Entry Model Of FX）の
**公表されている言語化ルール**を機械化したもの（`engine/strategies/wemof.py`）。
独自インジケーターのコードは一切使っていない、ゼロからの実装。

要点は「BB ±3σ タッチは*エントリー準備*であって、エントリーではない」という一点にある。
そのタッチが **説明できる**動き — 指標・要人発言などのヘッドライン、高値安値のブレイク、
ピボットやキリ番のブレイク — なら**見送る**。説明がつかない動きだけを逆張りする。

したがってこのアーキタイプの本体は 4 つの「説明フィルタ（veto）」であり、
それぞれ独立に ON/OFF できる。どれが本当に効くかは著者ではなく探索とゲートが決める:

| veto | 判定 | 意図 |
|------|------|------|
| `structure` | 直近 N 本の高値/安値をブレイク | 新値の値位置探索であって異常値ではない |
| `level` | キリ番グリッドに近接 | ストップ狩り・オプションバリアで説明がつく |
| `news` | 実体レンジ >> 直近 ATR | ヘッドライン起因のインパルスの代理指標 |
| `trend` | 上位トレンドと同方向 | 単なるトレンド継続で説明がつく |

**忠実性の限界（重要）**:

- `news` veto は本来「人間がニュースを読む」判断。ポイントインタイムの経済指標
  カレンダーが無いため**ボラティリティ急騰による代理**にした。意図は同じだが別物であり、
  そう明記してある。
- 決済は**バー終値のみ**で判定し、バー内では一切約定させていない。原法の
  「1〜2pips 利確 / 3〜8pips 損切り」は 5 分足 1 本の内側で決着するため、
  OHLCV だけから再現すると*起きたか分からない約定順序*を捏造することになる。
  終値決済は粗いがバイアスが無い。

#### 検証結果: 暗号資産では通らない（そして通ってはいけない）

veto の 16 通りを実データでゲートに掛けた結果 — **9 ファミリー中 0 通過**:

| family | best veto | sharpe | cpcv_med | cpcv_pos | dsr | pbo | 判定 |
|--------|-----------|--------|----------|----------|-----|-----|------|
| BTC/JPY:1h | SLNT | −2.83 | −2.92 | 0.00 | 0.00 | 0.33 | reject |
| BTC/JPY:1d | −−N− | 0.99 | 1.09 | 0.80 | 0.76 | 0.31 | reject |
| ETH/JPY:1d | −−−T | 1.32 | 1.32 | 0.93 | 0.83 | 0.22 | reject |
| XRP/JPY:1h | SLNT | −1.48 | −1.69 | 0.00 | 0.00 | 0.60 | reject |

ゼロコストでの切り分けで分かったこと:

1. **σ 乖離の平均回帰は暗号資産には存在しない。** 全銘柄・全足・全 σ で
   コスト 0 でもシャープは負かゼロ近傍。暗号資産では ±3σ の飛び出しは
   *継続*する（モメンタム）。
2. **veto 自体は宣伝通り効いている。** BTC/JPY 1h グロスで veto 無し −61.8% →
   全 veto −16.3%、取引数 1762 → 162。悪いトレードを正しく削っている。
   ただし土台の逆張りに優位性が無いので、削っても赤字がゼロに近づくだけ。

つまり **WEMOF は資産固有の手法**であり、原法が USD/JPY を指定しているのは飾りではない。
暗号資産に移植すると前提そのものが壊れる。ここで暗号資産向けにパラメータを
いじって黒字に見せることもできたが、それは本リポジトリのゲートが防ぐために
存在する当のオーバーフィッティングなので、やっていない。

#### USD/JPY 日足では「正しい方向」に出る — ただしサンプルが足りない

同じゲートを FRED `DEXJPUS`（日足 763 本）に掛けると:

| コスト | sharpe | cpcv_med | cpcv_pos | dsr | pbo | MinTRL | 判定 |
|--------|--------|----------|----------|-----|-----|--------|------|
| FX 実勢 1bps | 1.37 | 1.36 | **1.00** | 0.60 | 0.33 | **30,858** | reject |
| 暗号資産並 15bps | 0.90 | 0.91 | 0.80 | 0.21 | 0.33 | inf | reject |

アウトオブサンプル 15 分割の **100% が黒字**という、暗号資産とは正反対の姿。
それでも落ちる理由は **MinTRL = 30,858 本** — このシャープを統計的に確立するには
日足で約 122 年分が要る、とゲートが言っている。763 本では話にならない。

**したがって `wemof` を検証可能にする唯一の道は USD/JPY の分足データ**である。
3 年分の 5 分足 ≈ 225,000 本で、MinTRL が現実的に満たせる領域に入る。
日足でいくら粘っても構造的に通らない。

### 2. `trade_balance` — 日米の輸出入実績から USD/JPY を張る

仮説: 貿易収支は**投機ではない実需の通貨需要**である。日本の輸出企業がドル建て売上を
円転すれば円買い、輸入（とりわけドル建てのエネルギー）は円売り。日本の収支が悪化する
局面では、この構造的なフローが持続的な円供給に変わる。米国側も対称に効く。
よって**両国の収支の差分**が USD/JPY への遅い基礎的な圧力になる
（`engine/features/macro_trade.py` + `engine/strategies/trade_balance.py`）。

#### この層が独立している理由 — 発表ラグ

`context.yaml` の他の系列は全部**市場価格**で、プリントした瞬間に既知になる。
貿易統計は違う。**終わった月**を記述し、数週間後に公表される:

- 日本（財務省貿易統計）: M 月速報が **M+1 月 20 日**前後
- 米国（Census/BEA FT-900）: M 月分が **M+2 月の第 5 営業日**前後 — 約 5 週間後

**FRED は観測値にその期間の初日を刻む。公表日ではない。** そのまま結合すると
1 月の貿易収支を 1 月 1 日に読めてしまう。米国系列で 2 か月超の先読みであり、
これだけで壮麗かつ完全に架空のバックテストが作れる。この層は全観測値を
**公表された日**に写像してから結合する。ラグは意図的に**実際より遅め**に取ってある
（遅れれば優位性が少し削れるだけだが、早ければ優位性を捏造する）。

これは `tests/test_macro_trade.py::test_no_lookahead_features_depend_only_on_already_released_data`
で性質として固定してある: カットオフ以降に公表された観測値を全部消して再計算しても、
カットオフ以前の特徴量が 1 ビットも変わらないこと。さらに
`test_period_stamped_join_would_have_leaked` が**その検査自体を検査**する —
素朴な期間スタンプ結合なら本当に先読みが起きることを確認し、
「データが滑らかすぎて差が出ないだけ」で通ってしまう事故を防ぐ。

#### 現状: データ待ちで未検証

`trade macro-status` が同期状況を出す。本セッションでは 4 系列とも未取得のため、
特徴量は中立 0.0 に縮退し、戦略は**フラットのまま**（設計通りの安全側）。
FRED の系列 ID が廃番/改称された場合も同じ挙動になり、`macro-status` に
`MISSING` として出る — 「なぜか一度も取引しない戦略」という無言の故障にはならない。

同期後に検証するには（USD/JPY はどのブローカーでも扱えないので universe には入れない）:

```bash
uv run trade sync-data
uv run trade macro-status                       # まず 4 系列が揃ったか見る
uv run trade validate --strategy trade_balance \
    --symbol DEXJPUS --source fred --timeframe 1d --fee-bps 0.5 --slippage-bps 0.5
```

### 運用に出すために足りていないもの → 前提条件は解消済み

前回の記録では (1) USD/JPY の分足データ源と (2) FX の執行会場が無いと書いた。
どちらも実装した。

#### (1) データ: Dukascopy の無料ティック（`engine/data/dukascopy.py`）

`datafeed.dukascopy.com` は 1 時間 1 ファイルの LZMA 圧縮ティックを、
キーもアカウントも無しで 2003 年から配信している。これを 5 分足に集約する。

- URL の**月は 0 始まり**（1月 = `00`）。ここを間違えると*エラーにならず別の月が返る*
  という最悪の壊れ方をするので、テストで固定してある。
- 1 レコード 20 バイト・ビッグエンディアン（ミリ秒オフセット / ask / bid / 各出来高）。
  価格は整数ポイントで、**JPY クロスは 3 桁、他は 5 桁**でスケールする。
- ネットワークはテストの依存にしない。`tests/test_dukascopy.py` は
  同じバイナリ配置のペイロードを自前で組み立ててデコーダを通す。

**ティックを選んだ理由**は単なる好みではない。WEMOF は 0.2〜0.5pips のスプレッドに対して
1〜2pips を狙う手法で、**スプレッドがグロス優位性の 10〜50% を占める**。他人の分足
（仲値のみ）ではこれが完全に見えなくなる。このファイルは両サイドの気配を持つので、
`spread_stats_bps()` が**バックテストと同じデータから実コストを実測**できる。
仮定ではなく実測値を `--slippage-bps` に入れられる。

1 回の同期あたり `max_hours` 時間分（既定 1 週間）に制限してある。3 年の初回バックフィルは
約 26,000 リクエストで、無料ランナーの予算も無料フィードの礼儀も一度に壊す。
store は upsert なので、定期実行が追いつくまで履歴を伸ばし続ける。

#### (2) 執行: OANDA v20（`engine/execution/brokers/oanda.py`）

他のアダプタと同じ純 REST。常駐プロセスは不要。

- 既定は**練習環境**。実弾には `OANDA_PRACTICE=false` と `TRADE_LIVE_ENABLED` の
  **両方**が要る。変数 1 個の設定ミスでは実弾に届かない。
- v20 には「ポジションを設定する」API が無く、**基軸通貨の符号付き整数ユニット**を出す。
  既存の reconciler が計算している「現在と目標の差分」がそのまま v20 の要求と一致する。
- 端数ユニットは venue が拒否するので**ゼロ方向に丸める**（切り上げるとリスク上限を破る）。
- `clientExtensions.id` に決定的なクライアント注文 ID を載せる。v20 は重複 ID を
  拒否するので、遅延・重複した実行が二重約定にならない。
- v20 は long/short の脚を別々に返す（ヘッジ口座では両建てできる）ので、
  エンジンの符号付き 1 数量にネッティングして渡す。

#### 併せて直した 2 つの前提

**コストの資産クラス依存**（`RESEARCH_COSTS_BPS`）。研究ループは全銘柄に
暗号資産の 15bps を課していた。FX は手数料ゼロでコストはスプレッドのみ、
USD/JPY なら約 1bps。**15 倍の過大コストは実在する優位性を門前払いする** —
実際、日足の検証で 1bps ならシャープ 1.37、15bps なら 0.90 だった。
さらに検証時のコスト前提を `metrics` に記録し、昇格 FSM が**同じコストで**
フォワードを判定するようにした。でないと FX チャンピオンが
「劣化した」と誤判定されて退役する。

**研究対象に FX を追加**。`run_research` は暗号資産しか回していなかったので、
USD/JPY は永久に研究されなかった。

#### いまの手順

```bash
uv run trade sync-data          # Dukascopy から USD/JPY 5m が貯まり始める（数日で3年分）
uv run trade validate --strategy wemof --symbol USD/JPY --source dukascopy --timeframe 5m
uv run trade research --symbol USD/JPY   # 通れば incubating へ
```

**残っているのは検証そのもの**。5 分足が貯まるまで WEMOF の合否は分からないし、
`trade_balance` は FRED の貿易統計 4 系列が揃うまでフラットのままである。
どちらも「コードが足りない」状態ではなくなったが、**まだゲートを通っていない**以上、
チャンピオンではなく実弾も出ない。そこは data-sync が回ってからの判断になる。

## データ保存: 分足を月別に分割した理由（実測付き）

USD/JPY の 5 分足を追加したことで、**このリポジトリが `data/` を git にコミットする**という
設計と分足の頻度が噛み合わなくなった。3 年分 = 約 225,000 本 = **9.9MB** の 1 ファイルを、
data-sync が 30 分ごとに数本追記するためだけに丸ごと書き直す。

### まず見積もりが間違っていた

「圧縮バイナリだから git の差分圧縮は効かない、1 コミット ≒ 1 ファイル分の新規 blob」
と見積もると **約 475MB/日**になる。実際に測ったら**違った**:

| 構成 | 1 日（48 コミット）あたりの pack 増加 |
|------|-----------------------------------|
| 分割なし | **12.3 MiB/日** |
| 月別分割 | **0.25 MiB/日** |

parquet に追記しても前方のデータページはバイト単位で保たれるので、git の差分圧縮は
よく効く。素朴な見積もりの約 1/40 だった。**それでも 12.3 MiB/日は年 4.5GB** で、
無料の公開リポジトリが持ち続けられる量ではない。

### 打ち手: 1 時間未満の足だけ月別ファイルにする

```
data/ohlcv/{source}/{symbol}/{tf}/{YYYY-MM}.parquet   # 1h 未満
data/ohlcv/{source}/{symbol}/{tf}.parquet             # 1h 以上（従来どおり）
```

追記で書き換わるのは**当月ファイル（約 260KB）だけ**になり、過去の月はバイト単位で
不変なので git は新しい blob を作らない。実測 **0.25 MiB/日 = 年 90MB**。

1h/4h/1d を分割しないのは、系列が小さくファイル数だけ増えて得がないため。
分割前に書かれた単一ファイルは読み込み時にそのまま扱われ、次の upsert で月別に
畳み込まれてから削除される（二重に存在する瞬間がない）。

### 却下: FX の同期を日次に落とす案

当初は「月別分割 **＋** FX 同期を日次に」を提案したが、測ってから取り下げた。

分割だけで 0.25 MiB/日まで下がっており、日次化の追加効果はほぼ無い。一方で**代償が大きい**:
Dukascopy は 1 回の同期で 1 週間分しか歩かない（`DEFAULT_MAX_HOURS`）ので、
30 分間隔なら 1 日あたり約 336 日分進み、**3 年のバックフィルが約 3.3 日**で終わる。
日次にすると**約 156 日**かかる。**47 倍の待ち時間を、すでに解決済みの問題に払う**ことになる。

サイズの問題はストア層で解いたので、同期頻度は速いままでよい。

## 深い履歴での再検証 — 前回の報告を訂正する

FRED のシード制限を外して USD/JPY 日足が **768 本 → 13,936 本（1971 年〜）** になった。
3 年で出ていた数字の多くが、55 年では別物だった。

### 訂正: WEMOF 日足の「アウトオブサンプル 100% 黒字」は小標本の産物だった

前回、763 本の日足で「OOS 15 分割すべて黒字、シャープ 1.37」と報告した。
**55 年で測り直すと消える。**

| 標本 | sharpe | cpcv_pos | pbo | dsr | 判定 |
|------|--------|----------|-----|-----|------|
| 763 本（3 年） | 1.37 | 1.00 | 0.33 | 0.60 | reject |
| **13,936 本（55 年）** | **0.06** | 0.60 | **0.51** | 0.00 | reject |

PBO 0.51 は「イン・サンプル 1 位の選択はコイン投げ」の意味。55 年・182 トレードで
シャープ 0.06 なら、日足の σ フェードに優位性は**無い**。

前回の報告は「USD/JPY では正しい方向に出ている」という論拠に 763 本の数字を使った。
その論拠は**取り下げる**。これは標本を増やせば消える種類の見かけの優位性で、
まさに本リポジトリのゲートが防ぐために存在するもの — 私自身が引っかかった。

ただし**この結果は WEMOF を否定しない**。WEMOF は 5 分足の手法であり、
DEXJPUS は 1 日 1 本の仲値（open=high=low=close）なので、
そもそも日中のオーバーシュートを表現できない。日足の結果は
「日足では判定できない」以上のことを言っていない。5 分足での判定はデータ蓄積待ち
（現在 4,283 / 約 225,000 本）。

### `trade_balance`: 弱いが本物の優位性

| 標本 | sharpe | cpcv_pos | pbo | spa_p | dsr | 判定 |
|------|--------|----------|-----|-------|-----|------|
| 768 本 | 1.25 | 0.60 | 0.43 ✗ | 0.78 ✗ | 0.24 ✗ | reject |
| **13,936 本** | 0.71 | **1.00** | **0.02 ✓** | **0.01 ✓** | 0.35 ✗ | reject |

深い履歴で **5 項目中 4 項目が合格に転じた**。とくに:

- **PBO 0.43 → 0.02**: 「1 位選びがコイン投げ」だった状態から「選択は頑健」へ
- **SPA p 0.78 → 0.01**: 多重検定補正後もベンチマークに勝つ
- **CPCV 黒字率 100%**

残るは **DSR 0.35（要 0.95）** だけ。シャープ 0.71 は本物だが、累積試行数で
デフレートした後の水準には届かない。**貿易フローには実在するが弱い優位性がある**、
というのが 55 年分のデータの答え。

シャープが 1.25 → 0.71 に下がったことも重要で、3 年の数字は上振れていた。

### 運用上の注意: `trade validate` は撃つたびに基準を上げる

DSR は**そのファミリーで過去に試した累積試行数**でデフレートする（`state/trial_ledger.json`)。
CLI の `validate` を 1 回撃つと grid 分だけ ledger が増え、**以後そのファミリーの合格基準が
恒久的に上がる**。上の 2 回で `trade_balance` は既に 864 試行を消費した。

探索的に何度も回す用途には CLI を使わず、`evaluate_matrix` を明示的な `n_trials` で
直接呼ぶこと（ledger を触らない）。上の WEMOF 再検証はそうしている。
これは設計どおりの挙動で、緩めてはならない — 覚えておくべき運用作法の側。

## `wemof_tick` — WEMOF をバー内決済で検証する

### なぜ作ったか: 5 分足の判定は「終値決済版」の判定でしかなかった

3 年分（226,183 本）の USD/JPY 5 分足が揃い、`wemof:USD/JPY:5m` の判定が出た。
**Sharpe −0.16 で不合格**。中身を分解するとこうなる（片道 1bps のコスト）:

| 設定 | 3 年のエントリー | コスト前 | コスト後 |
|------|-----------------|---------|---------|
| 探索が選んだ設定（veto 3 つ ON） | 35 回 | +0.48% | −0.22% |
| veto なし（素の ±3σ 逆張り） | 2,549 回 | +3.36% | −48.5% |

veto は 1 回あたりの粗利を約 10 倍（0.13 → 1.38bps）にしており、宣伝どおり効いている。
ただしこれは**終値でしか決済しない** WEMOF の判定である。原法の利確 1〜2pips・
損切り 3〜8pips は 5 分足 1 本の内側で決着するが、OHLCV からはどちらが先に付いたか
分からない。そこで `wemof` は意図的に終値決済にしていた（約定順序の捏造を避けるため）。
原法そのものを判定するには、バーの内側の値動きが要る。

### 何を足したか

| 部品 | 場所 | 役割 |
|------|------|------|
| bid/ask 経路データ | `engine/data/intrabar.py` | Dukascopy のティックから 1 分ごとの bid/ask 四本値と「新安値/新高値の最大ステップ」を保存 |
| バー内決済シミュレーター | `engine/backtest/intrabar.py` | 利確・損切り・時間切れを 1 分経路上で約定させ、5 分足ごとのリターンに戻す |
| アーキタイプ `wemof_tick` | `engine/strategies/wemof_tick.py` | `wemof` と**同じエントリー**（共通コード）に `tp_pips` / `sl_pips` / `max_hold` の決済を付けたもの |

5 分足ごとのリターン系列に戻すので、**検証ゲート（CPCV → PBO → DSR → SPA）は一切変えていない**。

### 約定ルール — 「解像度不足で負けることはあっても、勝ちを捏造しない」

ロングで書く（ショートは ask 側で鏡像）。

- **エントリー**: シグナルを出したバーの終値の直後の最初の気配の **ask**。次のバーが
  閉じるまで気配が来なければ（データ欠損・週末）シグナルは捨てる。
- **利確**: 約定値 + `tp_pips` の指値。bid の高値が届いた最初の 1 分で、**その値で**約定。
  1 分足が利確値より上で寄り付いても、有利な値では約定させない。
- **損切り**: 約定値 − `sl_pips` の逆指値。1 分足がそれより下で**寄り付いたら始値で約定**
  （ギャップ損は全額払う）。それ以外は `max(損切り値 − bid_low_step, bid 安値)` で約定。
  その 1 分の中で損切りを発動させたティックは必ず「その分の新安値」なので、実際の約定は
  損切り値から `bid_low_step` 以上は下に離れない。つまりこの値は**実際の約定より有利にならない**。
- **同じ 1 分で利確と損切りの両方に触れた**: 順序が分からないので**損切り扱い**。
- **時間切れ**: `max_hold` 本後の最初の気配の bid で成行決済。データ末尾は最後の bid で決済。

この組み合わせで「各トレードの損益は、同じトレードをティック単位で再生した損益以下」が
成り立つ。`tests/test_intrabar_sim.py` が、ギャップ・急変・スプレッド拡大を混ぜた合成
ティックで**ティック単位の参照実装と全トレードを突き合わせて**これを検証している。
同じテストで測った解像度のコスト:

| 決済理由 | ティック単位との差 |
|---------|-------------------|
| 利確・時間切れ・ギャップ損切り | **完全一致** |
| 通常の損切り | 平均 **約 0.26pip 不利**（最大の新安値ステップで下限を取るため） |
| 利確と損切りが同じ 1 分（損切り扱い） | 合成データで全トレードの **0.6%** |

### コスト: スプレッドは実測、上乗せは執行会場との差だけ

スプレッドは経路データの bid/ask そのものから払う。従来の FX 研究コスト（片道 1bps）は
仲値バックテストでスプレッドの代わりをしていた数字なので、そのまま使うと**二重取り**になる。
上乗せするのは「データの気配（Dukascopy）」と「実際に注文を出す会場（OANDA の標準価格で
1pip 前後）」の差だけで、**片道 0.3bps（150 円で約 0.45pip、往復約 0.9pip）**とした
（`INTRABAR_COSTS_BPS`）。Dukascopy の USD/JPY スプレッドは実データで**中央値 0.6pip・
上位 10% で 0.9pip**（2023-08〜11 の 1 分足終値で実測。当初の想定 0.2〜0.5pip より広い）
なので、往復の総コストは**約 1.5pip**になる。会場の実勢より広めで、意図的に保守側に倒している。
もっと狭い会場を使うなら `--fee-bps/--slippage-bps` で明示する。仮定として狭くすることはしない。

### 正直な会計 — ゲートを緩めない仕掛け

- **試行数を `wemof` から引き継ぐ**。エントリーの探索空間は `wemof` と同じなので、
  `wemof_tick:USD/JPY:5m` の DSR は自分の累積試行数に `wemof:USD/JPY:5m` の累積
  （現在 1,480）を足してデフレートする。新しい名前で台帳をリセットさせない。
- **経路のバックフィルが 95% に届くまで研究しない**。届かない夜は探索の前に飛ばすので、
  台帳を一切消費しない（部分データで毎晩試行を積むと、本番の判定前に基準だけ上がる）。
- **5 分足だけ**。原法の足であり、1h/1d で試行を積まない。
- **研究専用**。ペーパー/実弾の執行系は「バーの終値ごとに目標ポジションを 1 回設定する」
  仕組みで、cron は数分遅れる。バー内の OCO 注文は出せないので、ゲートを通っても昇格させない
  （`research_only`）。アルファプール（ensemble）の部品にもしない。実運用するなら常駐プロセスか
  ブローカー側の OCO が必要で、それは設定変更ではなく別のシステムになる。

### 分かっている限界

- **レイテンシはゼロ扱い**。エントリーは「バーが閉じた直後の最初の気配」。実運用でこれに
  近づけるには 1 秒未満の反応が要る。この一点だけは楽観側に倒れている。
- 損切りの約定は上限付きの悲観値で、正確ではない（上の表）。毎分の新安値列を全部保存すれば
  正確にできるが、可変長列の複雑さに見合わないと判断した。
- 検証に使う bid/ask は Dukascopy の気配で、実際の会場の気配ではない（コストの上乗せで近似）。

### データと運用

- 保存先: `data/intrabar/dukascopy/USD_JPY/1m/{YYYY-MM}.parquet`。整数ポイント・相対値・zstd で
  **月 約 0.4MB**（合成ティックでの実測。3 年で約 14MB と 5 分足ストアと同じ桁）。
  生ティック（3 年で約 1.5GB の見積もり）は git に載らない。
- 取得: `trade sync-data` が経路も伸ばす。新規の経路は 5 分足の先頭（2023-08）から始まる。
  1 回の取得量は **30 日分**（`BACKFILL_MAX_HOURS`）で、5 分足の 1 週間分より大きい。
  理由は cron の実態で、`*/30` と書いてあっても GitHub が間引くため、このリポジトリでは
  **1 日約 5 回**しか動いていない（2026-09-23〜10-05 の実測で 1 日 4〜7 回）。1 週間分では
  3 年分のバックフィルに約 31 日かかるが、30 日分なら**約 1 週間**で揃う。リクエスト総数
  （と、それに使う Actions の分数）はどちらでも同じで、1 日あたりの要求数（約 3,600）も
  1 週間分の予算が想定していた量（約 8,000/日）を下回る。追いついた後は前回からの数時間分だけ。
- 実運用での実測（マージ後の最初の 3 回、2026-10-06）: 1 回 18〜44 分で 30 日分ずつ進み、
  取得に失敗した時間（タイムアウト等）は**飛ばされたまま再取得されない**。最初の 4 か月分で
  41 時間（約 2%）が欠け、期間内のカバー率は 97.3%。研究開始の基準（95%）は満たすが、欠けた
  時間に出たシグナルは約定できずに捨てられる。欠損の時間帯に偏りは見られない。
  経路の仲値は、欠けていない分については 5 分足の終値と完全に一致した（同じティック由来の確認）。
- Actions の分数: バックフィル中は data-sync 1 回あたり +15〜40 分。3 年分で合計おおよそ
  700 分の一時的な追加になる（1 回あたりの取得量を変えても総量は変わらない）。
- 状況確認: `trade intrabar-status`（カバー率と「研究対象か、バックフィル待ちか」）
